2 L'architecture en une image

Le Cerveau décide, le pont traduit et signe, chaque worker n'exécute que sur sa plateforme. Les clés de trading ne sont que dans les workers ; le Cerveau n'a ni clé ni accès sortant.

Pourquoi cette séparation Si un worker est compromis, l'attaquant touche une seule plateforme et une seule clé, sans droit de retrait. Si le Cerveau est compromis, il n'a aucune clé d'exchange à voler. Le reporter de positions est un service à part, en lecture seule, justement pour ne pas donner Redis aux workers qui portent des clés de trading.

Terminal SSM · serveur

Créer les secrets (sur le serveur seulement)

Pourquoi : les secrets n'ont jamais été dans Git. Les générer sur le serveur, directement dans les fichiers, évite qu'ils passent par votre PC, votre presse-papiers ou un chat. umask 077 crée les fichiers lisibles par le seul propriétaire ; le script de déploiement refuse des fichiers lisibles par tous.

umask 077 && printf 'CLIENT_ID=nothierly-prod\nDB_USER=nothierly\nDB_PASSWORD=%s\nREDIS_PASSWORD=%s\n' "$(python3 -c 'import secrets;print(secrets.token_hex(32))')" "$(python3 -c 'import secrets;print(secrets.token_hex(32))')" > .env
umask 077 && printf 'NOTHIERLY_ZMQ_SECRET=%s\n' "$(python3 -c 'import secrets;print(secrets.token_hex(32))')" > platform.env && : > reporter.env
python3 scripts/generate_curve_keys.py --clients hyperliquid bybit binance --out-dir secrets/curve
ls -la .env platform.env reporter.env secrets/curve

Vérification : les trois fichiers affichent -rw------- ; secrets/curve contient un fichier par client plus curve_server.env.

Pourquoi DB_USER=nothierly et pas un long mot de passePostgreSQL limite les noms d'utilisateur à 63 caractères. Un identifiant de 64 caractères hexadécimaux est tronqué en silence et peut causer des erreurs d'authentification difficiles à comprendre.
Pourquoi reporter.env est videLe script exige que le fichier existe. Vous le remplirez (clés de lecture seule Bybit et Binance, adresse Hyperliquid) quand vous activerez le reporter de positions.

Terminal SSM · serveur

Démarrer la collecte de données

Pourquoi seulement ces services : le Shadow Run sert à accumuler des données réelles (VPIN, carnet) pour entraîner les modèles. Les workers d'exécution n'y servent à rien, et sans clés de testnet ils quittent au démarrage et sont relancés en boucle par Docker, ce qui sature le CPU et noie les journaux.

SERVICES="redis-broker timescaledb nothierly-agents nothierly-vpin-tracker nothierly-maintenance" bash scripts/deploy_shadow.sh --up

Ce que fait le script, dans l'ordre : vérifie Ubuntu, l'espace disque (50 Go libres minimum) et la RAM, installe Docker si besoin, vérifie que .env, platform.env, reporter.env et secrets/curve existent et que les variables obligatoires y sont, crée les 4 volumes permanents, valide la configuration Compose, joue la maintenance à blanc, puis seulement démarre. Au moindre problème il s'arrête avant de démarrer et dit quoi corriger.

Sans --up il fait toutes les vérifications sans rien démarrer : utile pour un premier essai.

4 Les 5 plateformes : où en est chacune et pourquoi

Trois sont câblées et prêtes à tourner en dry-run. Deux ne peuvent pas l'être aujourd'hui, pour des raisons techniques précises.

Hyperliquid

PRÊT · dry-run testnet
Pourquoi ce worker
Bourse décentralisée. Les positions d'une adresse sont publiques : le reporter de positions n'a besoin d'aucune clé. Un « agent wallet » signe les ordres et ne peut pas retirer de fonds.
Variables
HL_ACCOUNT_ADDRESS (adresse du compte), HL_AGENT_SECRET (lu seulement avec --live), HL_VAULT_ADDRESS si vous tradez via un vault.
Fichier
platform.env pour le worker ; reporter.env pour le reporter (adresse seulement).
Particularité
Les fills sont suivis par WebSocket (avec ping applicatif et garde-fou de fraîcheur). Le VPIN peut aussi venir d'Hyperliquid (--source hyperliquid) : jamais les deux sources pour le même symbole, elles écriraient la même clé avec des flux différents.
Activer
Ajouter les variables, puis démarrer nothierly-platform-bridge et nothierly-worker-hyperliquid (testnet, dry-run par défaut).
Passer en réel
Éditer la commande du worker dans docker-compose.platform.yml : ajouter --live ; sur mainnet aussi --network mainnet --i-understand-real-funds. C'est une modification volontaire du fichier, pas une variable d'environnement : une faute de frappe dans un .env ne peut pas envoyer un ordre réel.

Bybit

PRÊT · dry-run testnet
Pourquoi ce worker
Futures USDT linéaires, API REST signée. Le worker vérifie au démarrage les droits de la clé (/v5/user/query-api) et refuse une clé qui a le droit de retrait.
Variables
Worker : BYBIT_API_KEY, BYBIT_API_SECRET (sans droit de retrait). Reporter : BYBIT_READONLY_API_KEY et _SECRET, une autre clé en lecture seule.
Particularité
Par défaut seuls les symboles ouverts au copy-trading sont acceptés ; --allow-non-copy-symbols lève cette limite. Mode de position « one-way » seulement (le mode hedge est refusé). Bybit n'accuse que la réception d'un ordre : la confirmation vient du WebSocket des fills.
Risque à vérifier
Restrictions par pays de l'adresse IP du serveur (Japon). Je ne l'ai pas vérifié : testez avec le dry-run avant de décider de la région.
Limites de débit
HTTP 429 : le worker dort exactement la durée de Retry-After. Les autres signaux de limite de Bybit (code dans le corps JSON, HTTP 403) ne sont pas traités.

Binance

PRÊT · dry-run testnet
Pourquoi ce worker
Futures USDⓈ-M. Le worker lit les précisions de chaque contrat (exchangeInfo), refuse une clé avec droit de retrait et un compte en mode hedge (il ne gère que le mode one-way).
Variables
Worker : BINANCE_API_KEY, BINANCE_API_SECRET (« Enable Reading » pour la vérification, « Enable Futures » pour ordonner, jamais le retrait). Reporter : BINANCE_READONLY_API_KEY et _SECRET.
Particularité
Les fills arrivent par le flux utilisateur (ORDER_TRADE_UPDATE), dont la clé d'écoute est renouvelée. HTTP 429 : pause exacte ; HTTP 418 (adresse IP bannie) : pause plus l'alerte immédiate.
À savoir
L'adresse du réseau de test de Binance est à confirmer dans la documentation (voir l'architecture, §4.5) : le testnet peut demander un ajustement.
Lien avec le VPIN
Le tracker VPIN lit les flux publics de Binance, sans clé. C'est lui qui révélera un blocage géographique depuis Tokyo (403 ou 451).

Darwinex

NON CÂBLÉ · Windows requis
Pourquoi pas sur Ubuntu
Le worker pilote MetaTrader 5 par le paquet Python MetaTrader5, qui n'existe que sous Windows et doit tourner sur la même machine que le terminal MT5. Aucun conteneur Linux ne peut le faire.
Ce qui existe
Le code du worker et ses tests (même socle que les autres : homme mort, alertes, état local). Il n'est pas dans les fichiers Compose.
Comment l'ajouter
Une machine Windows (instance EC2 Windows, ou votre PC) avec MT5 installé et connecté à Darwinex, qui lance le worker. Elle doit joindre le pont par le réseau : cela demande de publier le port du pont, d'autoriser cette machine dans le groupe de sécurité et de lui donner une clé CURVE. Rien de cela n'est préparé.
Pourquoi attendre
Chaque port ouvert est une surface d'attaque ; mieux vaut valider d'abord les trois plateformes Linux.

Numerai Signals

NON CÂBLÉ · aucun signal à envoyer
Pourquoi rien ne se passe
Le worker existe, mais le pont ne lui envoie rien : ses signaux sont destinés aux exchanges, et le worker Numerai les rejette (wrong_venue). Numerai attend un fichier de prédictions hebdomadaire, un tout autre produit.
Ce qui manque
Un producteur de prédictions Numerai (un modèle et un pipeline de soumission) : il n'existe pas dans ce projet. Je ne l'ai pas ajouté au Compose : il resterait inactif.
Variables (plus tard)
NUMERAI_* pour la soumission réelle ; en dry-run il écrit simplement les fichiers dans numerai_submissions.

Reporter de positions

À ACTIVER PLUS TARD
À quoi il sert
Au redémarrage, le moteur lit les positions réelles des plateformes et les adopte au lieu de repartir à plat. Sans lui, le pont enverrait « FLAT » et les workers fermeraient vos positions au marché, avec spread et frais.
Pourquoi un service à part
Le moteur n'a ni clé ni accès sortant ; les workers ont les clés de trading et n'ont volontairement pas Redis. Le reporter lit avec des clés en lecture seule et écrit une clé Redis : s'il est compromis, il ne peut pas trader.
Activer
Remplir reporter.env (modèle reporter.env.example), démarrer nothierly-position-reporter, puis ajouter NOTHIERLY_RECONCILE_VENUES=HYPERLIQUID,BYBIT dans .env (l'ordre est la priorité d'adoption).
Limite
Le prix d'entrée, l'ancre du stop suiveur et la date d'ouverture réels ne sont pas rapportés : après adoption, le stop repart du prix de marché. Cela efface le niveau de protection d'une position en gain et redonne une distance de stop neuve à une position en perte.

6 Pourquoi ces choix d'infrastructure

SSM plutôt que SSH

Aucun port entrant, aucune clé SSH à protéger, journal des actions. Vous n'êtes plus dépendant du port 22 de votre réseau.

m6i.xlarge plutôt que t3

Les instances « t3 » sont bridées quand leurs crédits de calcul s'épuisent, ce qui arrive vite avec 16 agents et de l'inférence. Les « m6i » ont une puissance constante. 16 Go de RAM : le moteur charge torch et FinBERT, et l'export de séries longues en demande aussi.

Volumes « external »

Un volume ordinaire disparaît avec docker compose down -v. Un volume external n'est jamais supprimé par Compose : perdre des semaines de VPIN exigerait une commande docker volume rm explicite.

Collecte sans workers au départ

Le but du Shadow Run est la donnée. Les workers sans clés de testnet redémarrent en boucle et saturent l'instance : on les ajoute plus tard, un par un.

Sans l'overlay docker-compose.prod.yml

Il met Redis, TimescaleDB et le moteur sur le seul réseau internal_core, que le tracker VPIN, le pont, le reporter et la maintenance ne rejoignent pas : ils perdraient l'accès à Redis et à la base. Les empiler suppose d'ajouter ce réseau à tous ces services (non fait, non testé).

Réconciliation désactivée par défaut

Activée sans reporter, le moteur attendrait des rapports qui n'arrivent pas. L'opt-in via NOTHIERLY_RECONCILE_VENUES garde le comportement historique tant que vous ne l'avez pas voulu.

Dry-run et testnet par défaut

Rien ne devient réel par accident : le passage en réel est une édition volontaire de la commande du worker, pas une variable d'environnement.

Maintenance planifiée

Rien d'autre ne purge : sans elle, TimescaleDB et les SQLite grossissent sans limite. Rétentions par défaut : VPIN 180 jours, bus 120 jours (compressé après 7). L'entraînement lit 30 jours : exportez avant de raccourcir une rétention.

9 Ce qui n'est pas vérifié

Soyez lucide sur ces points
  • Docker : aucun fichier Compose ni script de déploiement n'a tourné sous Docker. Le premier démarrage est le premier test.
  • Exchanges : les clients sont testés sur de fausses réponses, pas contre de vrais comptes. Les formes de messages viennent de la documentation.
  • TimescaleDB : les instructions de rétention et de compression sont construites et testées, jamais exécutées contre une vraie base.
  • SQLite partagé entre conteneurs : un fichier en mode WAL écrit par un conteneur et lu par un autre devrait fonctionner sur un volume local ; non vérifié.
  • Géographie : les restrictions de Binance et de Bybit selon le pays de l'IP ne sont pas vérifiées.
  • Pas de remote Git au moment de l'écriture : tant que vous n'avez pas poussé, le serveur ne peut rien cloner.
